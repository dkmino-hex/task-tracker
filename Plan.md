# План развития Task Tracker

## Текущее состояние

Приложение уже умеет:

- добавлять задачу с уникальным `id`;
- выводить все задачи или задачи с указанным статусом;
- обновлять и удалять задачу по `id`;
- переводить задачу в состояния `todo`, `in-progress` и `done`;
- хранить данные в `task.json`.

Сейчас весь код находится в `main.go`. Это нормально для первой рабочей версии, но с ростом проекта файл станет сложнее читать и изменять. Цель следующих этапов — разделить ответственность, не меняя поведение CLI.

## Правило работы

После каждого маленького этапа выполнять:

```text
gofmt -w .
go test ./...
go vet ./...
go run . list
```

Не перемещать весь код за один раз. Перенёс одну группу функций — убедился, что проект собирается и команды работают — переходи дальше.

## Этап 1. Разделить один пакет на несколько файлов

На этом этапе все файлы остаются в одном пакете `main`. Импорты между файлами не нужны, потому что у них общий пакет. Это самый безопасный первый шаг.

Итоговая структура:

```text
task-tracker/
  main.go
  task.go
  storage.go
  service.go
  task.json
  go.mod
  README.md
```

### 1.1. `task.go` — модель данных

Перенести сюда:

- тип `TaskStatus`;
- константы статусов `todo`, `in-progress`, `done`;
- структуру `Task`.

Ответственность файла: только описание того, как выглядит задача. В нём не должно быть чтения файлов, работы с `os.Args` и печати сообщений.

Проверка: после переноса `go test ./...` должен завершаться успешно без изменения поведения команд.

### 1.2. `storage.go` — чтение и сохранение JSON

Перенести сюда:

- `dataFile`;
- `loadTasks`;
- `saveTasks`.

Ответственность файла: превратить `task.json` в `[]Task` и обратно. Хранилище не должно решать, какую команду запустил пользователь.

Доработки этого этапа:

- при повреждённом JSON возвращать понятную ошибку;
- подумать над более информативным именем файла, например `tasks.json`;
- проверить, что `task.json` создаётся при первой команде `add`.

### 1.3. `service.go` — действия с задачами

Перенести сюда:

- `addTask`;
- `listTasks`;
- `updateTask`;
- `deleteTask`;
- `markTaskDone`;
- `markTaskInProgress`.

Ответственность файла: изменять или выбирать задачи и возвращать результат/ошибку.

Первое улучшение после переноса: создать общую функцию поиска задачи по `id`. Она должна возвращать индекс задачи либо ошибку «задача не найдена». Тогда `update`, `delete` и смена статуса не будут повторять одинаковый цикл.

Второе улучшение: сделать одну общую функцию смены статуса. Команды `mark-done` и `mark-in-progress` будут передавать ей нужный статус, вместо почти одинаковой реализации дважды.

### 1.4. `main.go` — только CLI

После переноса оставить в `main.go`:

- функцию `main`;
- разбор `os.Args`;
- проверку количества аргументов;
- преобразование строки ID в число;
- `switch` по имени команды;
- печать ошибок и пользовательских сообщений.

Цель: `main.go` должен отвечать на вопрос «что запросил пользователь?», а не на вопрос «как изменить JSON-файл?».

## Этап 2. Улучшить CLI внутри пакета `main`

### 2.1. Централизовать справку

Сделать отдельную функцию `printUsage`, которая выводит все команды. Вызывать её, когда:

- команда не передана;
- команда неизвестна;
- пользователь передал неверное количество аргументов.

### 2.2. Проверять точное число аргументов

Текущие проверки вида «аргументов меньше нужного» пропускают лишние аргументы. Для команд с фиксированным набором параметров проверять точное число:

| Команда | Число элементов `os.Args` |
| --- | ---: |
| `add` | 4 |
| `update` | 5 |
| `delete` | 3 |
| `mark-done` | 3 |
| `mark-in-progress` | 3 |
| `list` | 2 или 3 |

### 2.3. Сделать единый стиль ошибок

Хорошее правило: сервисные функции возвращают ошибки, а выводит их пользователю только `main.go`. Тогда сообщения не дублируются и функции проще тестировать.

### 2.4. Единый формат времени

При добавлении задачи сохранить текущее время один раз и присвоить его одновременно `CreatedAt` и `UpdatedAt`. При обновлении задачи или статуса менять только `UpdatedAt`.

## Этап 3. Добавить тесты

Создать рядом с каждым файлом тестовый файл с окончанием `_test.go`.

Минимальный набор проверок:

- добавление первой задачи создаёт ID `1` и статус `todo`;
- добавление после удаления использует новый ID, а не повторяет старый;
- обновление меняет текст и `UpdatedAt`, но не `CreatedAt`;
- удаление существующей задачи работает, несуществующей — возвращает ошибку;
- перевод в `done` и `in-progress` меняет статус;
- фильтр списка выбирает нужный статус;
- повреждённый JSON даёт ошибку, а не приводит к потере данных.

Для тестов не использовать настоящий `task.json` из рабочей папки. Позже добавить возможность передавать путь к хранилищу, чтобы тест создавал временный файл.

Запуск тестов:

```text
go test ./...
```

## Этап 4. Перейти к пакетам

Делать это только после этапов 1–3. В Go папка обычно соответствует одному пакету.

Возможная структура:

```text
task-tracker/
  cmd/
    task-tracker/
      main.go
  internal/
    task/
      task.go
      service.go
    storage/
      json.go
  go.mod
  README.md
```

Назначение:

- `cmd/task-tracker/main.go` — точка запуска программы и CLI;
- `internal/task` — модель задачи и бизнес-правила;
- `internal/storage` — хранение в JSON;
- `internal` означает, что эти пакеты предназначены только для этого приложения.

Важно: после перехода к пакетам имена, используемые из другого пакета, должны начинаться с заглавной буквы. Например, `Task`, `StatusTodo`, `Load`, `Save`.

Не начинать этот этап, пока не комфортно с файлами одного пакета `main`: он требует понимания импортов, зависимостей и конструкторов.

## Этап 5. Улучшения функциональности

Выбирать по одной функции и завершать её полностью:

1. `mark-todo ID` — вернуть задачу в невыполненное состояние.
2. Приоритет: `low`, `medium`, `high`.
3. Дедлайн: хранить дату и выводить просроченные задачи.
4. Команда `show ID` — подробная информация по одной задаче.
5. Поиск: `search "текст"` по названию и описанию.
6. Сортировка списка по ID, статусу, дате создания или дедлайну.
7. Команда `clear done` с обязательным подтверждением.
8. Цветной вывод статусов — только после базовой стабильной версии.

Для каждой новой команды сначала добавить строку в справку, затем реализацию, затем тест и пример в README.

## Этап 6. Подготовить выпуск

1. Обновить `README.md`: описание, установка, все команды, примеры и формат `task.json`.
2. Запустить `gofmt`, `go vet` и тесты.
3. Собрать программу:

```text
go build -o task-tracker.exe .
```

4. Проверить запуск из `cmd.exe`:

```text
.\task-tracker.exe add "Купить продукты" "Молоко и хлеб"
.\task-tracker.exe list
```

5. Проверить работу в пустой директории, чтобы убедиться, что JSON создаётся автоматически.
6. Сделать коммит в Git с понятным сообщением, например `feat: add task tracker CLI`.

## Контрольный список перед сдачей

- [ ] Все требуемые команды работают.
- [ ] `task.json` содержит `id`, `description`, `status`, `createdAt`, `updatedAt`.
- [ ] Некорректный ID не вызывает аварийное завершение.
- [ ] Неизвестная команда и статус дают понятную ошибку.
- [ ] Лишние аргументы не игнорируются молча.
- [ ] `go test ./...` и `go vet ./...` проходят.
- [ ] Исходники отформатированы `gofmt`.
- [ ] README содержит примеры запуска.
